# Spec-Kit Constitution — Phase II (Full-Stack Todo Web App)

## Core Principles

### Spec-First Enforcement
Always read relevant specs before planning or implementation. Reference specs explicitly using `@specs/...`. If requirements are missing, ambiguous, or conflicting, STOP and propose a spec update before coding.

### Mandatory Agentic Workflow
Every feature MUST follow this exact sequence: 1. Read specs 2. Generate implementation plan 3. Break plan into atomic tasks 4. Implement tasks incrementally 5. Validate against acceptance criteria 6. Report completion and gaps. Skipping or merging steps is forbidden.

### No Manual Coding
All code MUST be generated by the agent. The user will not write, modify, or fix code. Errors, bugs, or test failures MUST be diagnosed and resolved autonomously by the agent.

### Phase II Scope Lock
Implement ONLY Phase II features: full-stack web app with authentication. Do NOT implement chatbot, MCP tools, or Phase III functionality. Do NOT add features not explicitly defined in specs.

### Authentication & Security (Non-Negotiable)
All API endpoints require a valid JWT. JWTs are issued by Better Auth on the frontend. FastAPI MUST verify JWTs using a shared secret. User identity MUST come from the JWT, never from request payloads. Task ownership MUST be enforced on every CRUD operation. Unauthorized requests MUST return `401 Unauthorized`.

### Technology Lock
The following stack is mandatory: Frontend: Next.js App Router (16+), Backend: FastAPI (Python), ORM: SQLModel, Database: Neon Serverless PostgreSQL, Auth: Better Auth with JWT, Spec System: Spec-Kit Plus. No substitutions or shortcuts are allowed.

### API Contract Enforcement
API routes MUST match `@specs/api/rest-endpoints.md` exactly. Backend filtering MUST ensure users only access their own data. Errors MUST use FastAPI `HTTPException`.

### Monorepo Discipline
Frontend code lives ONLY in `/frontend`, Backend code lives ONLY in `/backend`, Specs live ONLY in `/specs`, Secrets MUST come from environment variables, No cross-layer leakage of concerns.

## Governance
Authority Hierarchy (Highest → Lowest): 1. This Constitution, 2. All files in /specs/**, 3. CLAUDE.md files (root, frontend, backend), 4. User prompts, 5. Model defaults. Higher authority rules override lower ones without exception. After each implementation step, the agent MUST report: Specs used, Tasks completed, Validation against acceptance criteria, Remaining risks or TODOs.
